Wait Type Reference Guide

Lock (LCK)LCK_M_S, LCK_M_X, LCK_M_U...Row/page/table lock contention. Indicates blocking chains, long-running transactions, or missing NOLOCK hints. Investigate with sys.dm_exec_requests and blocking session trees.
Disk I/OPAGEIOLATCH_SH, PAGEIOLATCH_EXBuffer pool reading pages from disk. High values indicate insufficient RAM (buffer pool too small), fragmented indexes causing full scans, or slow storage subsystem. Target: <5ms avg.
ParallelismCXPACKET, CXCONSUMERThreads waiting for parallel query coordinator or consumer. CXPACKET=skewed work distribution. Tune MAXDOP and Cost Threshold for Parallelism. High values on OLTP = problematic.
MemoryRESOURCE_SEMAPHORE, CMEMTHREADQueries queued waiting for memory grants. Causes sort/hash spills to TempDB. Review max server memory, add RAM, or fix queries with inflated memory requests (missing statistics).
NetworkASYNC_NETWORK_IOSQL Server waiting for client to consume result set. Indicates slow application processing or network saturation. Use pagination, reduce result set size, or investigate client-side bottlenecks.
LatchPAGELATCH_*, LATCH_EXIn-memory page contention (not disk). PAGELATCH_UP on allocation pages = TempDB contention (add temp files). PAGELATCH_EX on user pages = hot page bottleneck.
CPU/SignalSOS_SCHEDULER_YIELD, SLEEP_TASKCPU-bound: threads yielding the scheduler voluntarily. High SOS_SCHEDULER_YIELD = CPU pressure, tight compute loops, or missing indexes causing full scans. Scale CPU or add indexes.
Other/IdleWAITFOR, BROKER_*, XE_*Background/benign waits. WAITFOR=sleep loops. Service Broker and XE waits are infrastructure overhead. Usually safe to ignore unless they dominate the wait profile unexpectedly.

RPO Trend — Secondary Lag over 24h (monitor.sqlserver_rpo_1min)

< 5s
Excellent — near-zero data loss risk
5–30s
Acceptable — monitor network and log volume
> 30s
Critical — data loss risk; investigate now

RPO = maximum potential data loss (in seconds) if primary fails at this instant. Driven by log send queue size and network throughput.

RTO Estimate — Redo Queue over 24h (monitor.sqlserver_rto_1min)

< 60s
Fast failover — secondary is nearly caught up
1–10 min
Moderate lag — consider redo thread tuning
> 10 min
High lag — secondary has large redo backlog

RTO = estimated time for secondary to apply redo queue after a failover. High values = slow disk, high write volume, or undersized secondary.

HA Concepts Quick Reference

Synchronization States
SYNCHRONIZED — Secondary is current; zero-loss failover possible
SYNCHRONIZING — Secondary is catching up; some data loss possible
NOT SYNCHRONIZING — Replication paused or broken; investigate immediately
REVERTING / INITIALIZING — Joining or recovering; monitor progress
Key Health Signals
Log Send Queue — bytes unsent to secondary; high = network bottleneck
Redo Queue — bytes to apply on secondary; high = disk/CPU lag on replica
Failover Ready — is_failover_ready: Yes = no data loss risk on failover
Avail Mode — SYNCHRONOUS_COMMIT = safe; ASYNCHRONOUS_COMMIT = performance trade-off
